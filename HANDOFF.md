# Передача и сопровождение сайта Ольги Широкоступ

Этот документ — точка входа для Ольги и любого будущего агента или разработчика. Он описывает не только команды, но и принятые решения, которые легко случайно сломать при локально «правильной» правке.

## 1. Что передаётся

- Публичный сайт: <https://shirokostup.site/>
- Канонический репозиторий: <https://github.com/anton-gorokhovatsky/shirokostup>
- Публикация: GitHub Pages из ветки `main`, корень репозитория.
- Домен: `shirokostup.site`; привязка хранится в `CNAME`, HTTPS включён.
- Стек: статические HTML, CSS и JavaScript без CMS и серверной базы данных.
- Аналитика: Yandex Metrica, счётчик `111895186`, загружается только после согласия посетителя.

ZIP-архив проекта предназначен для быстрого восстановления файлов. Git bundle хранит полную историю репозитория и позволяет восстановить проект даже без доступа к GitHub. `node_modules`, отчёты тестов, `.git` и системные файлы в ZIP не входят.

## 2. Что Ольге нужно получить отдельно

Архив кода не передаёт права на внешние сервисы. До завершения передачи нужно проверить:

- собственный доступ Ольги к репозиторию GitHub с правом записи либо передачу репозитория в её аккаунт/организацию;
- доступ к регистратору домена, DNS-записям, автопродлению и контактному e-mail домена;
- доступ к кабинету Yandex Metrica для счётчика `111895186`;
- актуальный исходник CV и право заменять файл `assets/olga-shirokostup-cv.pdf`;
- резервную копию оригиналов изображений и подтверждение подписей/источников из `assets/images/CREDITS.md`;
- способ восстановления GitHub-аккаунта и домена без участия прежнего сопровождающего.

Токены, пароли, коды восстановления и доступы к домену нельзя добавлять в репозиторий или ZIP. Если появятся серверные интеграции, секреты нужно хранить в GitHub Secrets или в соответствующем внешнем сервисе.

## 3. Обязательное начало любой новой задачи

Будущий агент сначала читает:

1. `AGENTS.md` — обязательный порядок работы;
2. `ACCESSIBILITY.md` — выпускной порог WCAG 2.2 AA;
3. `DESIGN_PRINCIPLES.md` — визуальная и поведенческая система;
4. `EDITORIAL_STYLE.md` — голос, даты, подписи и экранная типографика;
5. `DESIGN_EVALS.md` — релевантные сценарии проверки;
6. этот документ и `README.md`.

Затем агент устанавливает фактическую исходную точку, не полагаясь на старый чат:

```bash
pwd
git remote -v
git status --short --branch
git log -5 --oneline --decorate
git fetch --prune
git status --short --branch
```

Перед визуальной правкой нужно открыть текущий публичный сайт и сохранить релевантный контрольный вид. Принятая публичная композиция является исходником: менять следует только запрошенную ось, не «улучшая заодно» соседние разделы.

## 4. Локальный запуск

Нужны Node.js 24, `pnpm` 11.9.0 и Python 3.

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm run build
python3 -m http.server 4173
```

Сайт откроется по адресу <http://127.0.0.1:4173/>.

Для браузерных тестов один раз устанавливаются движки:

```bash
pnpm exec playwright install chromium webkit
```

## 6. Типовые операции

### Обновить текст, ссылку или CV

1. Проверить факты и официальный вариант имени/названия.
2. Изменить исходный файл, сохранив семантику заголовков и понятное название действия.
3. Для CV заменить `assets/olga-shirokostup-cv.pdf`, не меняя ссылку без необходимости.
4. Запустить `pnpm run build` — сборка обновит cache key, если изменился CSS или JavaScript.
5. Проверить финальную строку в реальном макете, а не только в diff.

### Добавить предстоящее событие

Добавить объект в `content/events.json`, сохранив старые события как историю:

```json
{
  "id": "short-unique-id-2027-01-31",
  "title": "Full public event title",
  "ticketTitle": "Short title for the invitation",
  "kind": "Talk",
  "venue": "Official venue name",
  "city": "City",
  "startsAt": "2027-01-31T18:00:00+01:00",
  "archivesAt": "2027-02-01T00:00:00+01:00",
  "timeZone": "Europe/Stockholm",
  "url": "https://example.org/event"
}
```

Правила:

- `id` уникален и после публикации не меняется;
- `startsAt` содержит точное местное время и UTC-смещение;
- `timeZone` — корректная IANA-зона, например `Europe/Stockholm`;
- `archivesAt` определяет момент, когда приглашение исчезает и запись становится `Past event`; это не обязано совпадать с окончанием события;
- ссылка только HTTPS;
- `title` — полное название, `ticketTitle` — короткая версия для компактного приглашения;
- после изменения выполнить `pnpm run build`: HTML между `GENERATED:event-ticket` и `GENERATED:featured-event` создаётся автоматически и вручную не правится.

В `package.json` команды `build:check` и `check` содержат фиксированный `EVENT_RENDER_TIME`, чтобы результат проверки не менялся сам по себе с течением времени. При добавлении следующего события эту контрольную дату нужно один раз перенести внутрь жизненного цикла нового события — после архивации предыдущего и до `archivesAt` нового — и закоммитить вместе с данными события. Затем выполнить `pnpm run build` и `pnpm run check`.

В браузере событие пересчитывается по текущему времени. До `archivesAt` показывается ближайшее неархивированное событие; после этой даты билет скрывается, а секция остаётся как запись `Past event`. При нескольких будущих событиях используется ближайшее по `startsAt`.

### Добавить или заменить изображение

1. Положить качественный исходный JPEG в `assets/images/` с понятным стабильным именем.
2. Добавить источник, автора и контекст в `assets/images/CREDITS.md`.
3. Установить зависимости изображений и сгенерировать варианты:

   ```bash
   python3 -m pip install -r requirements-images.txt
   pnpm run images
   ```

4. Обновить соответствующий `<picture>` и `alt` в `index.html`. Для содержательного изображения `alt` описывает смысл в контексте; декоративное изображение получает пустой `alt`.
5. Проверить, что фотография не растянута, не обрезает значимый фрагмент и не вызывает скачок макета.

Не удалять оригинал после генерации: он является источником будущих форматов и размеров.

### Изменить стили

Редактировать только подходящий модуль в `styles/`, затем:

```bash
pnpm run build
```

`styles.css` и cache key в `index.html` должны попасть в тот же коммит. Если `pnpm run check` сообщает о stale generated assets, не исправлять итоговый CSS вручную — повторить сборку.

Сборка также синхронизирует cache keys в `404.html`. Не превращать её в параллельный мини-сайт: она использует общий `script.js`, общие настройки темы и движения и те же исходные модули в `styles/`. На GitHub Pages неизвестный адрес должен отдавать именно этот экран со статусом HTTP 404, а не стандартную страницу хостинга.

## 7. Хрупкие, но намеренные механики

### Стопки изображений

- В обеих стопках свайп или drag и вправо, и влево выполняет одно действие: верхняя просмотренная карточка уходит вниз, открывая следующую.
- Обе стрелки клавиатуры тоже продвигают стопку вперёд; это отражено в доступном имени.
- Вертикальный жест должен оставаться прокруткой страницы, а не перехватываться галереей.
- Подпись находится в нижней части карточки без «конских» пустых полей; изображения с документами используют `object-fit: contain`, фотографии — установленный для карточки режим.
- Поведение двух архивных разделов должно быть одинаковым, если контент не требует осознанного различия.

### Декоративная линия и курсор

- Canvas `.cursor-trail` — декоративный след, а не замена системного курсора. Он имеет `pointer-events: none` и исчезает над интерактивными элементами.
- Не добавлять глобальные нестандартные курсоры и браузерные «лечащие» хаки. Ссылки и кнопки используют стандартную механику указателя.
- Маршрут `.women-route` намеренно проходит поверх стопки изображений и имеет `pointer-events: none`. Не отправлять его под фотографии случайным изменением `z-index`, `overflow`, `isolation` или stacking context.
- Декоративная графика никогда не должна блокировать ссылку, drag, фокус или читаемость подписи.

### Типографика и линии

- Не воспроизводить конкретный перенос с помощью случайных `<br>` или неразрывных пробелов.
- Правила и подчёркивания не режут выносные элементы букв; native underline использует skip-ink, декоративная линия располагается ниже выносных элементов.
- Дисплейный шрифт и крупные заголовки проверяются целиком: ни одна буква, точка над `i` или нижний выносной элемент не может быть обрезан.

### Тема, движение и аналитика

- Сохраняются режимы System, Light и Dark; System продолжает реагировать на настройку ОС.
- `prefers-reduced-motion` и ручной выбор движения обязательны; содержательная информация не зависит от анимации.
- Yandex Metrica не загружается до выбора `Allow analytics`.
- Отказ включает `disableYaCounter111895186` и уничтожает активный счётчик. Не возвращать `<noscript>`-пиксель и не инициировать аналитику до согласия: это обойдёт выбранную механику приватности.
- Если меняется аналитический сервис или политика, одновременно обновить интерфейс согласия, публичное объяснение и тесты.

## 8. Правила для будущего агента

1. **Не доверять старому контексту без проверки.** Сначала репозиторий, ветка, diff, публичный сайт и актуальный viewport.
2. **Одна задача — одна ограниченная правка.** Не объединять исправление подписи, новый дизайн первого экрана и рефакторинг JavaScript.
3. **Сохранять принятую композицию буквально.** Не добавлять карточки, панели, новые фотографии, стекло или декоративные эффекты под видом общей полировки.
4. **Менять источник, а не результат сборки.** CSS — в `styles/`, событие — в `content/events.json`, изображения — из оригиналов.
5. **Реальный render обязателен.** Diff и зелёный тест не доказывают, что страница выглядит правильно.
6. **Проверять именно сообщённое разрешение.** Ближайший breakpoint не заменяет viewport, на котором замечена ошибка.
7. **Safari и физический iPhone имеют отдельный вес.** Playwright WebKit полезен, но не является окончательным доказательством качества touch-жеста в настоящем Safari.
8. **Доступность — выпускной порог.** Клавиатура, фокус, семантика, контраст, 320 CSS px, 200% текста, reduced motion и три темы не являются факультативной полировкой.
9. **Текст проверяется как интерфейс.** Сверять источник, роль Ольги, имена, даты, подписи, ссылку и фактический перенос в макете.
10. **Не публиковать вслепую.** Push, CI и Pages — стадии выпуска; завершение подтверждает только повторное открытие затронутой публичной композиции.
11. **Не удалять пользовательские изменения.** При грязном worktree отделить свою правку; не применять `git reset --hard` или массовый откат.
12. **Найденный повторяемый дефект превращать в проверку.** Тест должен защищать поведение, а не один случайный пиксель скриншота.

## 9. Пропорциональная проверка

Для любой правки:

```bash
pnpm run build
pnpm run check
```

Далее выполнить один релевантный сценарий из `DESIGN_EVALS.md` и один сфокусированный browser test/render. Для изменения общей типографики, токенов, движения, темы, навигации или правил агента — полный набор design evals и браузерных тестов:

```bash
pnpm run test:browser
```

Минимальная ручная проверка затронутого интерфейса:

- desktop и фактический проблемный viewport;
- 390 × 844 и 320 CSS px;
- 200% размер текста/reflow;
- System, Light и Dark;
- клавиатура и видимый фокус;
- reduced motion;
- отсутствие горизонтального overflow, обрезки, наложений и ошибок console;
- полный соседний контекст, а не только увеличенный фрагмент.

Для touch-галереи после изменения жеста нужна проверка в реальном мобильном Safari.

## 10. Выпуск

Текущая публикация устроена просто: push в `main` запускает `Quality gate`, а GitHub Pages публикует корень ветки `main`.

Рекомендуемый порядок:

1. `git status --short --branch` и просмотр точного diff;
2. сборка и пропорциональные проверки;
3. релевантный реальный render после последней правки;
4. осмысленный небольшой commit;
5. push в `main` либо PR, если меняется общая механика;
6. дождаться зелёных `Quality gate` и `pages build and deployment`;
7. открыть <https://shirokostup.site/> без старого кэша;
8. проверить затронутую публичную композицию и отсутствие ошибок console;
9. для изменённых CSS/JS убедиться, что публичные cache keys и файлы соответствуют локальной сборке.

Команды для наблюдения:

```bash
gh run list --repo anton-gorokhovatsky/shirokostup --limit 10
gh run watch RUN_ID --repo anton-gorokhovatsky/shirokostup
```

Зелёная автоматизация не заменяет визуальное принятие. Формулировка «готово» уместна только после публичной проверки.

## 11. Восстановление из архивов

### Из ZIP

```bash
unzip olga-shirokostup-site-*.zip
cd olga-shirokostup-site
corepack enable
pnpm install --frozen-lockfile
pnpm run check
```

ZIP не содержит Git-историю. Новый репозиторий при необходимости создаётся отдельно.

```bash

git remote set-url origin NEW_REPOSITORY_URL
```

Перед заменой `origin` нужно создать новый пустой репозиторий или получить актуальный URL существующего.

## 12. Разумное развитие проекта

Пока обновления редкие, статическая архитектура остаётся преимуществом: она быстрая, прозрачная и почти не требует обслуживания. Не нужно переносить сайт в CMS только ради эпизодической замены события или CV.

Если Ольга начнёт самостоятельно часто добавлять проекты, тексты и события, следующий безопасный шаг — вынести больше содержимого в проверяемые JSON/Markdown-структуры и генерировать существующую разметку без изменения принятого визуального языка. Сначала следует описать реальный редакционный процесс, затем выбирать CMS; не наоборот.
